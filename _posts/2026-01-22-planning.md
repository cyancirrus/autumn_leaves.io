## Planning-Perception-Action (PPA)
![Compression and Planning](./assets/compression_plan.png)

Planning-Perception-Action (PPA) is a closed feedback loop for robotic systems. I’ve been developing a navigation project that uses this loop, with the goal of enabling a robot car to autonomously navigate noisy, complex environments.
But we start simple - building this from scratch one step at a time. To tackle this problem, we need the PPA loop, but what exactly is it?

**Simply:**

```text
loop {
    *plan* a path for moving from the current position to the destination
    while plan_not_blocked {
        - sensors _*perceive*_ the environment and may block the plan
        - control _*actions*_ to follow the plan in the environment
    }
}
```

## Base Primitives Needed for Search

Before diving into algorithms, let’s define some key terms to make the discussion of search more precise.

#### Graph Primitives

> **Node** := A point within our representation  
> **Edge** := A connection between two points  
> **Graph** := A collection of nodes and edges where all points are fully reachable

Graphs are often characterized as follows:

**Edge Classification**
> **Directed** := A graph where edges have a unique direction, e.g., A → B  
> **Undirected** := A graph where an edge implies both directions are valid, e.g., A ↔ B

**Cycle Constraints**
> **Acyclic** := The graph contains no cycles by definition  
> **Cyclic** := The graph may contain cycles (even if a specific instance doesn’t)

**Examples**
> **Grid** := A cyclic undirected graph where each node has 4 neighbors  
> **Binary Tree** := An acyclic directed graph where each node has 2 neighbors  
> **Singly Linked List** := A directed graph where each node has 1 neighbor and can be pushed or popped

Hopefully this terminology isn’t too intimidating! Looking at these examples, you can probably imagine other graphs in everyday life - like a family tree, a subway map, or even a flowchart for a process.

## Search Basics - Depth First Search and Breadth First Search

Now that we have the base preliminaries out of the way, let’s dive into search algorithms.

### What is Search?

For search, we need two extra pieces of information:

- **Source** := The current location within the graph  
- **Target** := A condition which, when satisfied, halts the search

---

### Node Representation in Rust

Let’s first look at how we can represent a node in Rust. `Box` is used here as a pointer to the heap, which allows Rust to handle recursive types cleanly:

```rust
struct Node<T> {
    value: T,
    neighbors: Vec<Box<Node<T>>>,
}
```

---

### Stopping Condition

For example, suppose our goal is to “find the node with value 5”.
Starting at a node, we would:

1. Look at the neighbors
2. Explore each neighbor recursively (or in order)
3. Stop when we find the target

Pseudo-code:

```text
while (there are neighbors to explore) {
    if node.value == 5 {
        return "We found it!"
    }
}
return "Sadly, 5 does not appear in the graph"
```

---

### Exploring Neighbors

Finally, the way we explore neighbors determines the type of search:

* **Depth-First Search (DFS)** explores as far as possible along one branch before backtracking.
* **Breadth-First Search (BFS)** explores all neighbors at the current depth before moving deeper.

This distinction is what shapes the structure and efficiency of the search.

---

### Search Basics - Depth First Search (DFS)

DFS is straightforward: when exploring a neighbor, we follow a path as far as possible before backtracking.

```rust
fn depth_first_search(origin: Node<T>, search_value: T) -> bool {
    let mut stack = vec![origin];

    while let Some(node) = stack.pop() {
        if node.value == search_value {
            return true;
        }

        for neighbor in node.neighbors {
            stack.push(neighbor.clone());
        }
    }

    false
}
```

Recall that a **stack** is Last In First Out (LIFO), so DFS explores the deepest nodes first.

---

### Breadth First Search (BFS)

BFS looks almost identical, but we explore nodes closest to the origin first:

```rust
fn breadth_first_search(origin: Node<T>, search_value: T) -> bool {
    let mut queue = VecDeque::from([origin]);

    while let Some(node) = queue.pop_front() {
        if node.value == search_value {
            return true;
        }

        for neighbor in node.neighbors {
            queue.push_back(neighbor.clone());
        }
    }

    false
}
```

BFS simply changes the underlying data structure from a stack to a queue. This changes the order in which neighbors are explored:

* Nodes added earlier (closer to the origin) are explored first.
* Queue = First In First Out (FIFO) → wide exploration.

---

### Comparing DFS and BFS

* DFS searches **deep and narrow**
* BFS searches **shallow and wide**

Both DFS and BFS will find a node if it exists.
*However*, they differ in efficiency, especially when we want the **shortest path**:

* If the target location is known (e.g., navigating from home to the grocery store), BFS guarantees shortest-path discovery on a uniform-cost grid.
* DFS may explore deeply in unhelpful directions first, which can be inefficient.

This is the first glimpse of planning: choosing a search strategy impacts **both correctness and efficiency**.

---

### Dijkstra's – Optimization Under Different Edge Weights

Let’s revisit our simple example: *“I am trying to navigate from my home to the grocery store.”* The key idea is that *not all paths are created equal*.

* For drivers, one path might use a highway, another a less congested street, or even a back road to avoid traffic.
* For walkers or bikers, a different path might minimize red lights or intersections, even if it’s longer in distance.

Even in this simple scenario, BFS (Breadth-First Search) can fail to find the optimal path because it assumes all edges are equal. So, what’s the solution?

Dijkstra’s algorithm is structurally similar to BFS and DFS but introduces a critical change: it accounts for **edge weights** to always explore the cheapest path next.

```rust
type MinHeap = BinaryHeap<MinNode>;
type Neighbor<T> = Vec<(usize, Box<Node<T>>)>;

// Node prioritized by minimum cost in MinHeap
struct MinNode<T> {
    cost: usize,
    node: Box<Node<T>>,
}

// Graph node with value and neighbors
struct Node<T> {
    value: T,
    neighbors: Neighbor<T>,
}

fn dijkstras_algo<T: PartialEq>(origin: Node<T>, search_value: T) -> bool {
    let mut p_queue: MinHeap = MinHeap::new();
    p_queue.push(MinNode {
        cost: 0,
        node: Box::new(origin),
    });

    while let Some(current) = p_queue.pop() {
        if current.node.value == search_value {
            return true;
        }

        for (weight, neighbor) in &current.node.neighbors {
            p_queue.push(MinNode {
                cost: current.cost + *weight,
                node: Box::new(neighbor.clone()),
            });
        }
    }

    false
}
```

> **Note:** `MinNode` is required because Rust’s default `BinaryHeap` is a max-heap. You could also use `Reverse` or implement the necessary traits to compare nodes by cost. A `MinHeap` guarantees that the smallest element is popped first by implementing the `Ord` trait; internal ordering is not guaranteed.

Here’s a quick illustration in pseudo-code:

```rust
min_heap.push(3);
min_heap.push(1);
min_heap.push(4);
min_heap.push(2);

while let Some(value) = min_heap.pop() {
    print!("{value} ");
}
// Output: 1 2 3 4
```

The key insights from Dijkstra’s algorithm:

* Every neighbor we push onto the heap is considered in **order of cumulative cost**.
* The next node we explore always has the **lowest total cost from the start**, ensuring we find the optimal path.

This guarantees that the algorithm finds the **globally optimal plan**-the most efficient path to the goal. Note that there might be multiple equally optimal paths, but the path produced is guaranteed to be one of them.

### A\* – Using Heuristics and Approximate Knowledge

Great! We’ve now found the **best path** using Dijkstra. But you might be thinking:

> “Sure, we found the plan, but like BFS, we explored *too much information*.”

And you’re exactly right. Dijkstra examines **every possible path** in order to guarantee optimality-but often we don’t need to be that exhaustive.

Designing a heuristic function under non-uniform edge weights is genuinely difficult.
We must try to not overestimate remaining cost, as doing so removes A\*’s guarantee of optimality.
In many real modeling scenarios maintaining strict distance function coherence becomes impractical given the complexity of the cost model and the application itself, and near impossible when constrained by partial information.
However, this does not imply that A* is without value in such settings; its usefulness depends on the modeling intent and the constraints of the problem.


Let’s return to our navigation example: finding the best route from home to the grocery store.

**What we know:**

* The destination is fixed.
* Distances are measurable (we’re in Euclidean space).
* Each location/node is known.

#### Introducing Distance Functions

We can formalize “closeness” to our destination using a **distance function**:

* The hypotenuse of a triangle is never longer than the sum of its sides:
  ```
  let a = x0 -> x1;
  let b = x1 -> x2;

  distance(a + b) <= distance(a) + distance(b)
  ```
* Distances are never negative:
  ```
  distance(a) >= 0
  ```

For simplicity, we’ll use two intuitive options:

1. **Euclidean distance** (straight-line distance):
   ```
   Euclidean = sqrt(dx^2 + dy^2)
   ```
2. **Manhattan distance** (grid-based distance, only right-angle moves):
   ```
   Manhattan = dx + dy
   ```

Since we’re thinking about **city navigation**, Manhattan distance is ideal-it matches the right-angle grid of streets and accounts for obstacles like buildings.

#### A\* Algorithm: Combining Cost and Heuristic

Now that we can estimate how close a node is to the goal, we can **prioritize nodes** in our search. This is the essence of A\*: instead of using only `g` (distance from start, like Dijkstra), we order nodes by:

```
f = g + h
```

* `g` = cost from the start to this node
* `h` = heuristic estimate of cost from this node to the goal

Here’s how this looks in Rust:

```rust
type MinHeap = BinaryHeap<MinNode>;
type Coord = (usize, usize); // x, y location on the grid
type Neighbor<T> = Vec<(usize, Box<Node<T>>)>;

struct Node<T> {
    coord: Coord,
    neighbors: Neighbor<T>,
}

// Heap ordered by f = g + h
struct MinNode<T> {
    f: usize, // total estimated cost
    g: usize, // cost from start
    node: Box<Node<T>>,
}

fn heuristic_choice(start: Coord, end: Coord) -> usize {
    // Manhattan distance
    start.0.abs_diff(end.0) + start.1.abs_diff(end.1)
}

fn a_star_algo<T>(origin: Node<T>, target: Node<T>) -> bool {
    let mut p_queue: MinHeap = MinHeap::new();
    let h0 = heuristic_choice(origin.coord, target.coord);

    p_queue.push(MinNode {
        g: 0,
        f: h0,
        node: Box::new(origin),
    });

    while let Some(current) = p_queue.pop() {
        if current.node.coord == target.coord {
            return true;
        }

        for (weight, neighbor) in &current.node.neighbors {
            let g_new = current.g + *weight;
            let h_new = heuristic_choice(neighbor.coord, target.coord);
            let f_new = g_new + h_new;

            p_queue.push(MinNode {
                g: g_new,
                f: f_new,
                node: Box::new(neighbor.clone()),
            });
        }
    }

    false
}
```

#### Key Takeaways

* A\* explores **paths closer to the goal first**, guided by the heuristic.
* While not guaranteed to be **globally optimal** if the heuristic overestimates, even heuristics merely approximately admissible often produce very good paths quickly.
* In most real-world applications, A\* finds a **very intelligent path** quickly-perfect for navigation or games where absolute optimality is less critical.

### D\*Lite – Path Repair and Stored Knowledge

This section is a bit more conceptual. For actionable code, see my [D\*Lite implementation](https://github.com/cyancirrus/sabrina/blob/main/src/algo/d_star.rs).

> Note: This implementation uses a **QuadTree for compression**, assuming an underlying grid. My robotics implementation may not fit every use case exactly.

We’ve come a long way! We have a great plan, we’re considering only the most promising directions, and we’re finding the best path using weighted edges and heuristics.

But what happens if we’re on our way to the grocery store and suddenly… there’s a **road closure**?

Sure, we could recompute a new plan from scratch. But wouldn’t it be smarter to **reuse information from our previous plan** to update only what changed?

#### Conceptual Steps

Like A\*, D\* Lite prioritizes promising nodes using a heuristic, and like Dijkstra, it accounts for weighted edges

1. You have an idea of how to get to the grocery store.
2. You see a road closed.
3. Since the blockage is local, only paths crossing the closed road need updating.

D\*Lite formalizes this idea. Instead of planning from **Source → Target**, we plan from **Target → Source**, then reconstruct the plan from the source using neighbors with **lowest cost** (costs are lower closer to the target).

**High-Level Steps:**

* Create a **distance map** from target → source.
* Construct the plan by navigating to neighbors with lower distances from source → target.
* Investigate only promising nodes (like A\*) and account for **edge weights** (like Dijkstra).

This will define whether we are using Depth First Search (DFS) or Breadth First Search (BFS).


### Searchg Basics - Depth First Search

Depth First Search (DFS) is pretty straight forward and is exactly what one would expect. When exploring a neighbor we go down the entire line of a singular chain.

```rust
fn depth_first_search(origin:Node<T>, search_value:T) -> bool {
    let mut stack = vec![origin];
    while let Some(node) = stack.pop() {
        if node.value == search_value {
            return true;
        }
        for neighbor in node.neighbors {
            stack.push(neighbor.clone());
        }
    }
    false
}
```

Recall a stack is Last in First Out (LIFO), so we are looking at the deepest part of the changes. 
Breadth First Search (BFS) looks almost identical but we simply wish to explore nodes closest to the origin

```rust
fn breadth_first_search(origin:Node<T>, search_value:T) -> bool {
    let mut queue = VecDeque::from([origin]);
    while let Some(node) = queue.pop_front() {
        if node.value = search_value {
            return true;
        }
        for neighbor in node.neighbors {
            queue.push_back(neighbor.clone());
        }
    }
    false
}
```

Breadth First Search just changes the data structure which changes the order in which neighbors are added which changes the structure.
Nodes added earlier ie: closer to the origin as we pop First in First Out (FIFO) for the queue we explore widely.


Essentially, DFS searches deep and skinny, BFS searches shallow and wide.
Both DFS and BFS are functionally identical with respect to whether they will find a node.
*However*, crucially they are not identical with regards to efficiency with regards to path.

If instead of asking _does this node exist_ and we ask, what is the shortest path between my source and target. We then are starting to see glimpses of planning.

Sometimes the target is known, I am trying to navigate from my home to the grocery store -- The target is actually known in location in order to create a path we then can use search to define the best route.

As Breadth First Search, searches shallow and wide, we then know that for a grid with uniform cost that we are exploring a consistent wavefront.

_Our optimality is guaranteed... undereath these constraints... *But*..._

### Dijsktras - Optimiaztion Underneath Different Edge Weights

Our simple example for visualization "I am trying to navigate from my home to the grocery store", _not all paths are created equal_.

- For those driving they might be able to take a highway or a less congested street - or minimize traffic by taking the backway
- For those walking or biking perhaps one way will optimize the number of red-lights by including fewer intersections

Even our simplest example now breaks the optimality of our path for bfs. What are we to do?

Dijsktra's Algorithm is almost functionally identical to the two previous searches but with a key change
```rust
type MinHeap = BinaryHeap<MinNode>;
type Neighbor<T> = Vec<(usize, Box<Node<T>>)>;

// Prioritization Node in MinHeap
struct MinNode {
    cost:usize,
    node:Box<Node<T>>
}

// Graph node with value and edges
struct Node<T> {
    value: T,
    neighbors: Neighbor<T>,
}

fn dijkstras_algo(origin:Node<T>, search_value:T) -> bool {
    let mut p_queue:MinHeap = MinHeap::new();
    p_queue.push(
        MinNode {
            cost: 0,
            node: Box::new(origin),
        }
    });
    while let Some(current) = p_queue.pop() {
        if current.node.value == search_value {
            return true;
        }
        for (weight, neighbor) in current.node.neighbors {
            p_queue.push(
                MinNode {
                    cost: current.node.cost + *weight,
                    node: Box::new(neighbor.clone()),
                }
            );
        }
    }
    false
}
```
Note: MinNode is needed because rust's default compare for BinarHeap is greater. One would need to derive or implement several traits, or one could use Reverse.
A MinHeap is simply a datastructure which is ordered upon popping but not internally ordered and uses. Implementation details not covered here.

Eg Pseudo-code for brevity
```
min_heap.push(3);
min_heap.push(1);
min_heap.push(4);
min_heap.push(2);

while let Some(value) = min_heap.pop() {
    print!("{v:} "); 
}
```
would print to console `1 2 3 4 `

Okay, information changed a little but not drastically this is the same form. So lets consider now what his refinement gives us.

- Every neighbor we push onto the heap will be pushed in order
- Our next neighbor to look at will contain the lowest cost of _any_ other neighbors for that path

This guarantees us optimality in our path where edges can be different weights.
Fantastic! We now choose the best path for how to get there!

Note: the plan is globally optimum -ie it is the most efficient plan (not a unique plan, but the plan generated is optimal).


### A* - Using Heuristics and Approximate Knowledge

Great we have the best path we did so well!

But I hear you saying "Sure we found the plan, but we had the same problem with bfs, we explored _*too much information*_.
You're exactly correct.

If we comprimise some global optimality (for the plan) by considering the most likely candidates.
By updating only the most likely candidates we can lower our search complexity drastically.

Lets again think of our navigation to the grocery store, how might we find the best path from home?

Knowns
- We have a static fixed destination
- We are on euclidean space - distances should be defined
- We have a known location for each node.


Lets first talk of distance functions - not too deeply
- The hypoteneuse of a triangle can't ever be greater than the sides
>>  distance(a + b) <= distance(a) + distance(b)
- Distances should never be negative
>> distance(a) >= 0

There are better ways to formalize distance functions but for the purpose of this blogpost and given the current length we should be fine.

First question, which different function could we use?

We could use what would the straight line be between two points
>>  Euclidean :=  square_root( dx^2 + dy^2 );

Or we could imagine if I can only walk in right angles on a grid how long would the distance be?
>> Manhattan := dx + dy; 

As we're investigating city navigation, for our algorithm lets use manhattan distance!
The city blocks closely mirror the right angle constraint and may "straight lines" are blocked by houses and other obstacles.


Okay perfect! We now have a way to formalize "how close a node is to the end", this will help us prioritize different alternatives.
Remember, we are optimizing for the total path distance, which is while we'll be adding this _*heuristic*_ to the cost.

A* differs from Dijkstra only in that the heap is ordered by f = g + h rather than g alone.
```rust
type MinHeap = BinaryHeap<MinNode>;
type Coord = (usize, usize); // x,y location on the grid
type Neighbor<T> = Vec<(usize, Box<Node<T>>)>;

struct Node<T> {
    coord: Coord,
    neighbors: Neighbor<T>,
}

// Heap is ordered by f = g + h
struct MinNode {
    f: usize, // total estimated cost (g + heuristic)
    g: usize, // Dijkstras cost from start to this node
    node: Box<Node<T>>,
}

fn heuristic_choice(start: Coord, end: Coord) -> usize {
    // Manhattan distance :: dx + dy
    start.0.abs_diff(end.0) + start.1.abs_diff(end.1)
}

fn a_star_algo(origin: Node<T>, target: Node<T>) -> bool {
    let mut p_queue: MinHeap = MinHeap::new();

    let h0 = heuristic_choice(origin.coord, target.coord);
    p_queue.push(MinNode {
        g: 0,
        f: h0,
        node: Box::new(origin),
    });

    while let Some(current) = p_queue.pop() {
        if current.node.coord == target.coord {
            return true;
        }

        for (weight, neighbor) in current.node.neighbors {
            let g_new = current.g + weight;
            let h_new = heuristic_choice(neighbor.coord, target.coord);
            let f_new = g_new + h_new;

            p_queue.push(MinNode {
                g: g_new,
                f: f_new,
                node: Box::new(neighbor.clone()),
            });
        }
    }

    false
}

```

Superb! Now we are able to intelligently explore paths that are closer to our goal first.
While the inferred path with A\* does not have deterministic guarantees for global optimality, the algorithm itself is extremely quick and in practice does extremely well for cases where one does not need the absolute maximum - only a _very intelligent path_.

So we're doing really great, and this is the last section for this explore!

Back to our navigation from Home -> Grocery Store, we now have a great plan, we're considering only the most viable directions to help narrow down our search space and we're estimating the distance to path and we have weighted -> so we're finding the best route!

Perfect! ... almost, what happens if we're on our way to the grocery store and suddenly there's a road closure?
>> Well we could implement a new plan, from scratch right!

We definitely could and that's a valid strategy, but what happens if we could use information from our previous plan to help us generate the new one?

Lets take this step by step -> I have an idea of how to get to the Super Market, I see a road closed..

>> Presuming that the blockage is local ie just a street, what does my plan look like on the otherside?
>> The new information of seeing a blockage only updates paths which would cross through this new boundary

D\*Lite is essentially the formalization of this idea. Instead of navigating from Source -> Target ie Home -> Grocery Store, we create a map from Grocery Store -> Home.

Instead of recustruction of the plan using neighbors, we instead create the plan by starting at the source and looking at the neighbors and choose the neighbor with the lowest cost, lower costs being closer to our destination.

At a High Level
- Create a distance map from target -> source
- Create the plan from navigating to lower neighbors from source -> target

We wish to only investigate nodes going from source to target which are good candidates -> like A\*'s implementation, we would like to use this piece as well, and additionally use djisktras for the weight.
